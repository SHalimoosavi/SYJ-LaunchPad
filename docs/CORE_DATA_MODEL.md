# Core Data Model (Phase 3)

Normalized schema for the 9 entities beyond `User`/`Wallet` (Phase 2) and
`Project` (documented separately in `docs/PROJECTS.md`). Data model only —
no execution logic. See the module docstring in
`backend/app/features/core_data/models.py` for the full reasoning.

## Blockchain authority boundary

None of these tables are the source of truth for on-chain facts. `Sale`
describes *configured* parameters (price, caps, timing) — not a live
fundraising engine. `Purchase`/`Claim` are *recorded* amounts pending
independent on-chain verification in later phases. `Transaction.status`
has precisely defined, non-overlapping meanings (`pending` → `submitted`
→ `confirmed`/`failed`) specifically so nothing here can be read as
claiming on-chain finality the app hasn't actually observed via RPC —
that RPC integration doesn't exist yet (Phase 1 of the earlier "Sayanjali"
framing, not yet authorized in this roadmap).

## Entities

| Entity | Purpose | Owner boundary |
|---|---|---|
| `Sale` | Configured sale parameters for a `Project` | via project |
| `Transaction` | Generic blockchain reference record | `related_user_id` (nullable) |
| `Purchase` | Recorded purchase against a `Sale` | `purchaser_user_id` |
| `Claim` | Allocation/claim-accounting record | `user_id` |
| `Whitelist` | Sale eligibility record (no enforcement) | `user_id` |
| `ReferralReward` | Reward record (no attribution/payout engine) | `referrer_user_id` |
| `AuditLog` | Append-only security/action log | write-only, `actor_user_id` SET NULL on delete |
| `Notification` | User-facing notification data | `user_id` |
| `Setting` | Generic key/value app settings (never secrets) | `user_id` or global |

## Two things worth understanding before extending this schema

**Partial unique indexes.** Two constraints needed to be partial, not
plain `UNIQUE`, because of how Postgres treats `NULL`:
- `transactions`: `(chain_id, tx_hash)` unique only `WHERE tx_hash IS NOT
  NULL` — multiple `PENDING` transactions legitimately have no hash yet,
  and a plain unique constraint would still allow unlimited NULLs anyway,
  so this is really about being explicit rather than a correctness gap.
- `settings`: a plain `UNIQUE(user_id, key)` does **not** stop two global
  settings (`user_id IS NULL`) from sharing a `key`, because Postgres
  treats every `NULL` as distinct from every other `NULL`. A second index,
  `unique on key WHERE user_id IS NULL`, closes that gap. Both are tested
  (`test_duplicate_global_setting_key_is_rejected`).

**The secret-leakage guard.** `AuditLog.context` and `Setting.value` both
accept free-form data, which is exactly the kind of field a secret could
accidentally end up in. The database can't stop that — the check is in
`core_data/service.py`, rejecting any write where a key matches a
deny-list (`password`, `secret`, `private_key`, `seed_phrase`, `jwt`,
etc.) before it ever reaches the database.

## Migration gotcha (found and fixed during this phase)

Postgres native enum types (`sale_status`, `transaction_status`, etc.)
have an independent lifecycle from the tables that use them. Alembic's
autogenerated `downgrade()` drops the *table* but not the *type* — left
alone, `alembic downgrade base` followed by `alembic upgrade head` fails
with `DuplicateObjectError`. Both this phase's migration
(`fcb02142d0b6`) and the Phase 2 auth migration (`897d1f9340ca`, which
predates this phase but had the same latent bug) now explicitly drop
their enum types in `downgrade()`. Verified with a full fresh-database →
head → base → head cycle, not just a single-step downgrade.

## Testing

`app/features/core_data/test_core_data.py` — 34 tests against a real
Postgres instance. Not just "insert worked": FK-integrity failures
(nonexistent `project_id`), `CheckConstraint` violations (sale end before
start, self-referral), uniqueness violations (duplicate claim/whitelist
per sale+user, duplicate global setting key, duplicate tx hash per
chain), cascade-vs-SET-NULL behavior verified via a *second, fresh*
session (not the one that had the row cached in its identity map — see
inline comments for why that distinction mattered), and the
secret-leakage guard (parametrized across multiple secret-like key
patterns, plus a control case proving it doesn't over-reject benign keys).
